## Короткий ответ

Моделировать запрос как конечный автомат: idle → loading → success / error. Хранить data, error и status (а не булевы флаги), отменять запрос при размонтировании и гонках через AbortController, ошибки показывать с retry. В бою — React Query/SWR: кэш, дедупликация и состояния из коробки.

## Контекст

Практический вопрос про типовой код загрузки данных: интервьюер смотрит на состояния, гонки и отмену.

## Как строить ответ

### Модель состояний

Не isLoading+isError, а status: 'idle' | 'loading' | 'success' | 'error' — исключает невозможные комбинации. Данные и ошибка хранятся рядом.

### Загрузка в эффекте

useEffect → fetch → setState; cleanup с AbortController против гонок и setState после размонтирования. Зависимости эффекта = параметры запроса.

### Ошибки

try/catch + отдельная ветка UI с кнопкой «Повторить». Ошибки рендера — Error Boundary. Для rejected promise в Suspense/use() — тоже Error Boundary.

### Готовые решения

React Query/SWR: статусы, кэш, ретраи, дедупликация, фокус-рефетч. Свой хук useQuery — только когда библиотеку тянуть нельзя.

## Пример ответа

Я моделирую запрос конечным автоматом: status — idle, loading, success, error, плюс data и error. Это лучше разрозненных флагов: невозможно получить loading и error одновременно. В useEffect запускаю fetch, в cleanup отменяю через AbortController — это решает гонки, когда параметры меняются быстрее, чем приходят ответы. Ошибки делю на ошибки запроса — показываю inline с retry, и ошибки рендера — их ловит Error Boundary. В реальном проекте беру React Query: он из коробки даёт те же состояния, кэш, дедупликацию запросов и рефетч при фокусе, и самописный код сокращается до одного вызова useQuery.

## Частые ошибки

- Несколько булевых флагов с противоречивыми комбинациями
- setState после размонтирования компонента
- Игнорировать гонки при быстрой смене параметров
- Показывать спиннер вместо осмысленного состояния ошибки без retry
