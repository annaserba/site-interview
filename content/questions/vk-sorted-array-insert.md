## Короткий ответ

Бинарный поиск позиции за O(log n), затем splice(index, 0, value) — вставка со сдвигом за O(n). Итого O(n) на вставку против O(n log n) при push + sort. Если вставок много — массив не та структура: сбалансированное дерево или мультимножество дадут O(log n).

## Контекст

Мини-алгоритм: проверяют бинарный поиск и понимание асимптотики операций над массивом.

## Как строить ответ

### Бинарный поиск позиции

Делим диапазон пополам: ищем первую позицию, где arr[mid] >= value (lower bound). O(log n) сравнений.

### Вставка

splice(pos, 0, value) сдвигает хвост — O(n). На больших массивах это доминирует над поиском.

### Сравнение альтернатив

push + sort каждый раз — O(n log n) и потеря стабильности; держать массив сортированным вставками — амортизированно выгоднее при редких вставках.

### Когда массив не подходит

Частые вставки/удаления в отсортированном наборе — balanced BST (в JS нет из коробки), либо пересмотреть задачу: Map + отсортированный снапшот по требованию.

## Пример ответа

Оптимально: бинарным поиском найти позицию — first index, где arr[mid] >= value, это O(log n) сравнений, и вставить туда через splice(pos, 0, value). Сама вставка в массив стоит O(n) из-за сдвига элементов, но это всё равно лучше наивного push + sort за O(n log n), который к тому же разрушил бы уже упорядоченную структуру. Код бинарного поиска: lo = 0, hi = arr.length, пока lo < hi — берём mid, если arr[mid] < value, идем вправо, иначе влево; итоговое lo — позиция вставки. Важная оговорка: если вставок много, массив — неподходящая структура, потому что сдвиг O(n) на каждую вставку даст O(n²) суммарно; тогда нужно сбалансированное дерево поиска или другая структура данных.

## Частые ошибки

- push + sort после каждой вставки
- Ошибка на границах бинарного поиска (off-by-one)
- Забыть, что splice на миллионном массиве — это O(n)
- Не учесть дубликаты: вставлять до или после равных
