## Короткий ответ

Batching — группировка нескольких обновлений состояния в один ре-рендер. До React 18 батчились только обновления в React-обработчиках событий; в промисах, setTimeout и нативных слушателях каждый setState вызывал отдельный рендер (лечилось `unstable_batchedUpdates`). React 18 с createRoot включил automatic batching: обновления батчатся везде — в then-колбэках, таймерах, любых событиях. Выйти из батчинга можно через `flushSync`, когда нужен синхронный рендер и чтение свежего DOM.

## Контекст

Рендер — дорогая операция; три подряд setState в одном тике не должны давать три прохода reconciliation. Понимание батчинга объясняет, почему state «не обновился сразу после setState», и как это влияет на производительность.

## Как строить ответ

### Механика

- setState не применяется мгновенно: обновление ставится в очередь, React сливает их и делает один ре-рендер.
- Чтение state сразу после setState вернёт старое значение — берут функциональную форму `setX(prev => prev + 1)`.

### Что изменилось в React 18

- Automatic batching во всех контекстах: промисы, таймеры, нативные события.
- Работает только с createRoot (новый корневой API).

### Управление

- `flushSync(() => setX(...))` — форсировать синхронный рендер (редко: измерения DOM, скролл к новому элементу).
- Батчинг не объединяет разные компоненты в один рендер «бесплатно» — он про тики обновлений, а не про мемоизацию.

## Пример ответа

«Batching — это когда несколько setState в одном синхронном блоке сливаются в один ре-рендер. В React 17 это работало только в обработчиках событий, в промисах и таймерах каждый setState рендерил отдельно. React 18 с createRoot батчит всё автоматически, что заметно снижает число рендеров при загрузке данных. Побочка для понимания: state после setState читается старым, поэтому для зависимых обновлений использую функциональную форму. Если нужен DOM сразу после обновления — оборачиваю в flushSync.»

## Частые ошибки

- Читать state сразу после setState и ждать новое значение.
- Думать, что батчинг был всегда и везде.
- Злоупотреблять flushSync — он ломает оптимизацию.
- Путать батчинг с мемоизацией компонентов.
